# Flujo SDD (Spec-Driven Development)

El desarrollo de cualquier funcionalidad nueva en la secretaría virtual se hace siguiendo un pipeline de skills `/sdd-*` que transforma una idea informal en código implementado, pasando por etapas intermedias revisables. Cada etapa produce artefactos que sirven de input a la siguiente. El pipeline también sirve para **modificar un sistema/subsistema ya implementado**: la spec lo declara con la línea `**Modifica:** <capa>/<nombre>` bajo `# Objetivo` y desde ahí cada etapa aplica **semántica de delta** (lo no mencionado del código real se conserva) — sin esa línea todo funciona como siempre (greenfield).

## Pipeline lineal (orden de ejecución)

Estos cuatro skills se ejecutan **en este orden**; la salida de cada uno es la entrada del siguiente.

1. `/sdd-specification` — Punto de entrada del pipeline. Crea, mejora o revisa de forma interactiva (preguntando mucho al usuario) una especificación **multi-fichero** en lenguaje de negocio en `.sdd/drafts/YYYY-MM-DD_HH-MM_{nombre}/`: un índice `specification.md` (objetivo, actores, historias de usuario con sus **escenarios `ESC-NNN`** —semilla de los tests E2E—, tablas de enlaces a modelos y pantallas, seguridad, recursos y fuera de alcance), un `entity-<Nombre>.md` por cada modelo (campos, estados, restricciones `RES-NNN`, campos calculados `CC-NNN`, las **propiedades editables por acción `AllowProperties`**, y por evento validaciones `VAL-NNN` y reglas de negocio `RN-NNN`) y un `screen-<slug>.md` por cada pantalla (identidad, menú, paneles, botones, reglas de UI `RUI-NNN`). La historia de usuario va **embebida** en la propia spec (no hay fichero `user-story.md`). Se puede invocar varias veces sobre la misma spec; siempre pregunta si crear nueva / refinar la última / elegir otra, y sobre una spec existente si además hacer un review. La conversión a la capa técnica (taxonomía `V`/`R`/`U`, clasificación `cliente`/`servidor` por campo) y la materialización de los tests E2E las asume `/sdd-designer`. En una iniciativa que **modifica** un sistema existente, los `entity-*.md`/`screen-*.md` marcados como existentes declaran **solo el delta** (el código es la fuente de verdad del as-is; excepción: `AllowProperties` se declara siempre como lista resultante completa) y el barrido de historias propone escenarios de **no-regresión** de los flujos que el delta roza.
2. `/sdd-designer` — A partir de la spec multi-fichero (`specification.md` + `entity-*.md` + `screen-*.md`, sin fase de análisis), produce un plan de DISEÑO que describe qué clases, métodos, vistas y acciones hay que construir y dónde va cada regla, sin escribir todavía el código. Asume la conversión a la capa técnica: mapea cada regla del spec (`RES`/`VAL`/`RN`/`RUI`/`CC-NNN`) a la taxonomía `V`/`R`/`U` con trazabilidad `Origen spec`, clasifica cada campo `cliente`/`servidor` (apoyado en las líneas `Input AllowProperties` y los `CC-NNN` del spec) y **materializa `design/tests.md`** desde los escenarios `ESC-NNN` del spec. Si el `design/` ya existe, al re-invocarlo pregunta si **regenerarlo** o entrar en el modo **Revisar/Modificar** (valida frontmatter/XSD/cobertura/arquitectura/seguridad/tests y aplica cambios puntuales sin regenerar, preservando ediciones). En una iniciativa que **modifica**, los XML de filas `Acción: Modificar` se diseñan leyendo el fichero real como base y produciendo el **fichero completo resultante** (conservando lo preexistente salvo lo listado en `## Eliminaciones declaradas`), con criterio de **mínima intrusión** para el juez del torneo.
3. `/sdd-implementer` — Convierte el `design.md` en código real. Es un **MOTOR genérico y agnóstico al artefacto** (igual que `/sdd-designer` y `/sdd-specification`): el `SKILL.md` solo aporta el flujo y la orquestación de subagentes, y delega TODO lo específico de la implementación en `template-system/README.md` (configurable con `--template-dir`), que los subagentes leen como contrato. Lanza cuatro roles: un **descomponedor** que escribe las tareas atómicas (`implementation/task_NN.md` + índice `task.md`) y propaga `design/tests.md` a `implementation/tests.md`; tras la aprobación del usuario, un **implementador** por tarea que copia literalmente los XML materializados por el diseñador, delega el código Java en `developer-code-implementer` y **genera el código de los tests** (unitarios JUnit+Mockito desde `design/unit-test-desc.md`); y un bucle **verificador-build** → **corrector-build** que compila hasta que `./gradlew clean build` pase —lo que compila Y ejecuta esos tests unitarios— (máx 3 iteraciones; si tras la 3ª sigue sin compilar, para y pregunta al usuario). No ejecuta tests E2E — eso es de `/sdd-debug-with-test-e2e-desc`. En una iniciativa que **modifica**, un XML `Modificar` solo sobrescribe su destino tras una **comprobación de conservación** (ningún elemento preexistente se pierde sin estar en `## Eliminaciones declaradas`) y la conformidad de superficie se comprueba **por delta** del `git diff` (los métodos preexistentes de una clase modificada nunca se reportan ni se eliminan).
4. `/sdd-close` — Cierra la iniciativa. Deduce los sistemas/subsistemas que tocó la iniciativa **del `design.md` del draft** (campo `**Capa:**`, tabla de ficheros `Creado`/`Modificado`, FQN — **no usa `git diff`**, que con muchos commits sería frágil), incluida base/infraestructura si cambió. Lanza un **documentador** por sistema (en paralelo) que, **desde el código real** (el código es la única fuente del contenido), regenera en la raíz del sistema su `CLAUDE.md` + su `modelo.puml` (esquema PlantUML del modelo de datos derivado de los `domains/*.xml`) + su `modelo.png` renderizado. Después **mueve el draft verbatim** a `.sdd/archive/<nombre>`. No reescribe los artefactos del draft (no hay versión "as-built"): la documentación viva pasa a ser el `CLAUDE.md` por sistema. El `design.md` es input solo del **alcance**, no del contenido; lo específico de la documentación lo define `template-system/README.md` (configurable con `--template-dir`).

## Skills auxiliares (no forman parte del flujo lineal)

Estos no van en una posición fija del pipeline: se invocan cuando hace falta.

- `/sdd-debug-with-test-e2e-desc` — Ejecuta los tests E2E (`test-e2e-desc.md`, producido por `/sdd-designer`) contra la aplicación real. Se usa **después de `/sdd-implementer`** (el diseño y el código ya existen) y normalmente **antes de `/sdd-close`**. Es un **MOTOR genérico y agnóstico al artefacto** (igual que el resto del pipeline): el `SKILL.md` solo aporta el flujo y delega TODO lo específico en `template-system/README.md`. Lanza tres roles: un **descomponedor** que trocea `test-e2e-desc.md` en una carpeta `test-e2e-desc/` (un índice `tests-e2e-desc.md` con un checkbox por test + un `t-NNN-<slug>.desc.md` autocontenido por test); un **ejecutor** por test que lo pilota con `playwright-cli` contra la app real y devuelve `SUCCESS`/`FAIL`; y, ante un `FAIL`, un **corrector** que analiza el problema (con el log de la app), carga los skills que necesite y arregla el código Java (delegando en `developer-code-implementer`), reiniciando la app y reejecutando (**LIMIT** 10 ciclos por test). La app la gestiona el propio motor (tracked en segundo plano con `./run.sh`). Progreso reanudable por los checkboxes del índice (un test que pasa se marca `[x]`).
- `/sdd-create-tests-e2e` — **Persiste** como tests de regresión Playwright los tests E2E ya depurados. Se usa **después de `/sdd-debug-with-test-e2e-desc`** (necesita su carpeta `test-e2e-desc/` con los checkboxes) y normalmente **antes de `/sdd-close`**. Es un **MOTOR genérico y agnóstico al artefacto**: el `SKILL.md` solo aporta el flujo y delega TODO lo específico en `template-system/README.md`. De la descomposición toma **solo los tests que pasaron** (`[x]`) y, por cada uno, copia su `t-NNN-<slug>.desc.md` a `src/test/e2e/<iniciativa>/` (snapshot "as-tested" con cabecera-banner) y lanza un **generador** que escribe su `t-NNN-<slug>.spec.ts` hermano (mismo nombre base, misma carpeta; ciclo login→pasos→logout vía `src/test/e2e/_support/auth.ts`); el motor ejecuta el `.spec.ts` y, ante un fallo, un **sanador** arregla el `.spec.ts` (nunca el código Java; un fallo que solo se arregla tocando la app es una regresión que se reporta), **LIMIT** 8 ciclos por test. La app la gestiona el motor (`./run.sh` tracked). Idempotente: salta los tests cuyo `.spec.ts` ya existe (salvo `--fresh`). Al final ejecuta una **puerta de regresión**: corre toda la suite `src/test/e2e/`; un test de una iniciativa anterior en rojo se retira solo si el `design.md` lo declara en `## Tests E2E supersedidos` — si no, es una **REGRESIÓN** y se reporta al usuario.

## Flujo resumido

```
specification  →  design  →  implementation  →  close
                                  ↑
        (test E2E con /sdd-debug-with-test-e2e-desc → persistir con /sdd-create-tests-e2e)
```
